  <name>Task 1: Decision — freeze the ProductionSpec field contract (INP-01 "and scale")</name>
  <decision>Freeze the ProductionSpec field contract — does INP-01's "type and scale" need a numeric scale field?</decision>
  <context>
    `ProductionSpec` is the durable artifact of this phase. Phase 4 (cost localization), Phase 6
    (the real form), Phase 7 (the live-research request shape) and Phase 9 (the fixed reference
    production) all bind to it. Adding a field after Phase 4 starts consuming it means a
    coordinated change across four phases plus any persisted JSON; adding it now is free.

    The open question is INP-01's exact wording. `REQUIREMENTS.md` INP-01 and `PROJECT.md`
    line 41 both read *"production type **and scale** (feature / limited series / episodic)"*.
    The parenthetical lists exactly three values that read as the **type** axis. `03-RESEARCH.md`
    Assumption A2 and Open Question 1 flag that "scale" may be a second, unlisted dimension —
    episode or season count — and recommend a planner decision before Phase 6 builds the real
    form around it. Nothing in `03-CONTEXT.md`, `ROADMAP.md` or `ARCHITECTURE.md` disambiguates
    it.

    This is the only genuinely one-way door in Phase 3. Every other decision here is a YAML edit
    or a template change.
  </context>
  <options>
    <option id="type-only">
      <name>A — production_type enum alone (the research recommendation, and the default)</name>
      <pros>
        Smallest contract; ships today; matches the three values the requirement literally lists.
        Adding an episode-count field later is purely additive to a Pydantic model with a
        default, so no existing caller breaks — the cost is only that Phase 4's budget model and
        Phase 6's form both have to be revised together when it lands.
      </pros>
      <cons>
        A producer describing a limited series has no way to say how many episodes, which is the
        single largest scale driver for episodic work. If a judge notices the gap during the
        demo, it reads as an incomplete input model rather than a deliberate boundary.
      </cons>
    </option>
    <option id="type-plus-episodes">
      <name>B — production_type plus an episode_count required for limited_series and episodic</name>
      <pros>
        Closes "and scale" now, while it is free. Phase 4's budget model needs episode count to
        scale an episodic production at all, so this is a field that phase will certainly ask
        for. A cross-field validator (`episode_count` required when type is not `feature`,
        forbidden when it is) is one more validator in a file that already has three.
      </pros>
      <cons>
        Interprets "and scale" as a second dimension when the requirement's own parenthetical may
        simply be describing the enum. If wrong, the form carries a field nobody wanted — cheap,
        but visible on a public page.
      </cons>
    </option>
    <option id="type-plus-free-scale">
      <name>C — production_type plus a free-text scale field</name>
      <pros>Captures whatever the visitor means by scale without committing to an interpretation.</pros>
      <cons>
        Unstructured text cannot drive a budget model, so Phase 4 would have to parse it or
        ignore it. A field on the durable contract that no consumer can use is worse than no
        field. Not recommended.
      </cons>
    </option>
  </options>
  <resume-signal>Reply with "A", "B" or "C". Replying "A" is also the correct answer if you want to move fastest — it is the research recommendation and the additive-later path.</resume-signal>
</task>
