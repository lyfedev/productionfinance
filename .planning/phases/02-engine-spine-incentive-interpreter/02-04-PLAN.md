<objective>
Turn a gross credit into the cash that actually reaches the bank.

This is where the project's whole argument lives. A headline rate of 53 percent on an
£18,000,000 film looks like £9,540,000 and is actually about £5,380,000 — a 44 percent
overstatement — once the ceiling split, the core-expenditure cap and the corporation-tax
haircut are applied in the right order. Plan 02-05 landed the gross side of that
arithmetic. This plan implements the four conversion mechanisms, the cliff-tiered audit
fee, the corporation-tax deduction, and the arrival timing that has to be reported beside
the value — and closes the UK example on the net figure a producer actually banks.

Purpose: INC-06, INC-07, INC-08. Output: `engine/net_cash.py` complete, with the audit-fee
cliffs proven at both sides of both boundaries and the UK net figure under test.
</objective>

  <action>
Replace the three `NotImplementedError` stubs in `engine/net_cash.py` with the remaining
mechanism functions, and implement the audit fee and arrival timing that all four share.

Structure the module as four pure functions keyed by the `mechanism` value —
`refundable`, `transferable`, `rebate_grant`, `nonrefundable_credit` — each parameterised
by that programme's own numbers. Never one function per jurisdiction: the whole point of a
data-driven engine is that two jurisdictions both being transferable share one function and
differ only in their declared discount range.

The audit fee is a cliff lookup over `audit.fee_schedule`, structurally the same shape as
the rate band lookup plan 02-05 wrote in `engine/credit.py` — reuse that shape rather than
inventing a second one. Find the single band whose low threshold is at or below the
qualified spend and whose high threshold is above it or null, and deduct that band's fee.
Bands are half-open, so a spend exactly equal to a band's low threshold belongs to that
band and a spend exactly equal to a band's high threshold belongs to the *next* one. A
spend matching no band raises with a message naming the spend and the declared bands — a
schedule with a hole in it is a rule-file bug and must surface, not silently deduct
nothing. An empty schedule is a different thing entirely: it means no fee is modelled,
deducts exactly zero, and says so in a derivation line.

`transferable` converts a credit to cash at a broker discount. The declared range has a low
and a high rate and there is no sourced point estimate, so the result carries both bounds
and leaves `point` as `None`. A caller that wants one number must choose one deliberately
at its own call site. Presenting a midpoint here would be the same class of error as the
blended mean-error figure Phase 1 designed `accuracy_denominator_by_stage` specifically to
prevent. The derivation names both rates and the source note they came from.

`nonrefundable_credit` is the taxable path. Deduct the audit fee, then deduct corporation
tax at the programme's declared `corporation_tax_rate`. If `taxable` is true and the rate is
null, that is a validation error at load time, not a runtime default — add the cross-field
check to `engine/models.py` only if plan 02-01 did not already, and prefer a Pydantic model
validator over a runtime guard so the failure lands where the rule file is read. A
mechanism with `taxable` false emits a derivation line stating corporation tax does not
apply, so a reader can tell the step was considered rather than skipped.

`ArrivalTiming` is returned by all four. Where `timing.payout_lag.typical_days` is
declared, compute the estimated date by adding that many days to the run date and record
both the lag and the terms-lock point in the reason. Where it is null, the estimated date is
`None` and the reason names the jurisdiction and states the payout lag has no primary
source — New York is exactly this case today. Never derive a date from a lag the rule file
did not declare. Timing is displayed, never discounted to present value; that scope cut is
recorded in `jurisdictions/SCOPE-FREEZE.md` and no code here may quietly reverse it.

Quantise through `quantize_money` at the single point each net figure becomes reportable —
not at intermediate steps, where repeated rounding would accumulate.

Write `tests/fixtures/jurisdictions/synthetic-mechanisms.yaml` with `status`

mechanism, each declaring the fields its mechanism needs: a three-band audit fee schedule

Write `tests/test_engine_net_cash.py` covering the behaviours above. Parametrise the audit

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| YAML rule file → engine | Discount ranges, tax rates, fee schedules and payout lags all arrive as rule-file data and all directly move a reported cash figure |
| Engine → reported figure | This is the last stage before a number is presented as cash; a fabricated rate or a synthesised date here is indistinguishable from a sourced one downstream |
| Synthetic fixture → curated data | The UK fixture is the file most likely to be mistaken for a real jurisdiction model |
