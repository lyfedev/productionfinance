## Recorded decision — the ceiling split operates on core expenditure, before the cap

A discuss-phase would have locked this; there is none, so it is recorded here.

`02-RESEARCH.md` gives the blend function a signature taking a single base. The UK worked
example in `feasibility-incentives.md` shows a single base is not enough, and that two
plausible orderings give different answers:

- **Split the core expenditure first, then cap each slice.** £18,000,000 splits at the
  £15,000,000 enhanced ceiling into £15,000,000 and £3,000,000. Each slice is capped at 80
  percent, giving £12,000,000 and £2,400,000. Rates apply: £12,000,000 at 53 percent is
  £6,360,000, and £2,400,000 at 34 percent is £816,000. Gross **£7,176,000**. This
  reproduces the sourced figure.
- **Cap the whole base first, then split.** £18,000,000 capped at 80 percent is
  £14,400,000, which is entirely below the £15,000,000 ceiling, so all of it takes the
  enhanced rate: **£7,632,000**. Wrong, and completely plausible-looking.

**Decision: split first, cap each slice, then apply each slice's rate.** Reversibility:
`costly` — the ordering is internal to one function, but the `Core expenditure (pre-cap)`
input edge it depends on is guaranteed by plan 02-01 and consumed here, so changing it
means coordinating two plans.

The pre-cap core expenditure figure is reached through the `inputs` tuple of the
`QualifyingBase` Figure, at the entry whose `label` is exactly the string
`Core expenditure (pre-cap)`.

## Recorded decision — Connecticut's rate schedule is empirically derived, and says so

Connecticut's three-band rate schedule (10 percent from $100,000 to $500,000, 15 percent
from $500,000 to $1,000,000, 30 percent above $1,000,000) is not quoted from a statute page
in this repository. It was derived in plan 01-04 by computing the implied rate across every
row of Connecticut's own issued-credits open-data export filed under statute CGS 12-217jj —
85 rows in the first band, 37 in the second, the large majority in the third, with
essentially zero unexplained residue anywhere observed. That derivation is recorded in the
`notes` block of `tests/fixtures/validation_pairs/ct_christmas_always.yaml`.

This is a legitimate primary-government-data derivation, but it is a derivation, and the
rule file must say so rather than presenting the rates as quoted statute. The
`rate_structure.source_note` field exists for exactly this (RD-05 item 4). It must name the
dataset, its sha256, the statute filter applied, and the row counts behind each band.
