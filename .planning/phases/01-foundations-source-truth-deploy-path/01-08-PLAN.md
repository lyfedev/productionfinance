This plan lands the first three. It is also where the free-memory measurement D-22 calls for is taken — STATE.md flags it as gating the Milestone 2 data-layer decision, and it is only cheap to take at this exact moment.

Output: An isolated Python 3.12 at `/opt/prodfin/.venv`, a `prodfin` systemd unit running uvicorn on localhost as a dedicated non-root user, a `deploy.sh` that is the whole deploy path, and an executed reboot test.
</objective>

Reboot the box and watch it come back. This is a deliberately destructive check and it is the whole point of D-23: an enabled systemd unit that fails to start on boot is indistinguishable from a working one until the box actually restarts, and discovering that on day 15 is the failure this test exists to prevent.

Before rebooting, confirm the rollback position is intact — the pre-resize snapshot still reports `available` and the old instance is still stopped, per the 01-07 SUMMARY. Record the pre-reboot state: `systemctl is-active` for the prodfin unit, for Apache and for MySQL, and a successful `curl -I https://vockell.com`.

Issue `sudo reboot` over SSH. Expect the connection to drop; that is the reboot working, not a failure.

Poll for the box to come back. Do not touch anything on it while polling, and above all do not start the service manually — a manually started service proves nothing about boot behaviour. Wait for SSH to answer again, then check, in this order and without intervening:
- `systemctl is-active prodfin` reports `active`
- `curl -fsS http://127.0.0.1:8000/health` on the host returns 200
- `systemctl is-active` reports active for Apache and MySQL
- `curl -I https://vockell.com` from off the box returns 200

Record the elapsed time from the reboot command to the first successful health response.

If the service does not come back on its own, that is a real finding and the plan is not done. Read `journalctl -u prodfin` since boot and diagnose it — the usual causes are an `ExecStart` path that does not exist for the service user, a `WorkingDirectory` the user cannot read, an ordering problem where the unit starts before the filesystem or network is ready, or a missing `EnvironmentFile` that was not marked optional. Fix the unit in the repository, reinstall it, and reboot again. Do not paper over it with a `Restart=always` that masks a startup failure as a restart loop, and do not record the test as passing on the basis that the service can be started by hand afterwards.

Append the result to `deploy/README.md` under a "Reboot test" heading with the date, the elapsed recovery time, and the verbatim post-reboot check output.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → the host's open ports | Anything bound to the public interface is reachable by anyone; only 80 and 443 should be |
| `prodfin` service user → the rest of the host | A compromised application process must not be able to reach the LAMP stack's files or the database |
| public GitHub repository → `/opt/prodfin` | Code arrives on a production host by anonymous clone; whatever is in the repository runs on the box |
| uv-managed interpreter → system Python 3.9.2 | The isolation boundary that keeps Apache and MySQL working |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-41 | Elevation of Privilege | the service process's identity | high | mitigate | A dedicated non-login system user `prodfin` owns `/opt/prodfin` and is named in the unit's `User` and `Group`; the acceptance criteria assert `ps -o user= -C uvicorn` reports that user and not root or bitnami. |
| T-01-42 | Information Disclosure | uvicorn's bind address | high | mitigate | `ExecStart` binds `127.0.0.1` explicitly; the automated verify asserts a TCP connection to port 8000 from off the box fails. An unproxied, un-TLS'd application endpoint on a public IP would bypass every control plan 01-09 adds. |
| T-01-43 | Tampering | the system Python and the Bitnami tree | high | mitigate | uv manages its own interpreter under its own directory and no apt operation runs; the automated verify asserts the host's `python3 --version` still reports 3.9.2 and that vockell.com still returns 200. Recorded as a prohibition in `must_haves.prohibitions`. |
| T-01-44 | Information Disclosure | `/opt/prodfin/.env` | medium | mitigate | Mode 0600 owned by the service user, outside git's tracked set by the existing ignore rules, carrying no secret today so the ownership and mode are established before Phase 5 adds API keys. |
| T-01-45 | Tampering | code arriving on a production host | medium | mitigate | Anonymous HTTPS clone of the public repository, `git pull --ff-only` so a rewritten remote history fails rather than silently applying, and `uv sync --frozen` so the host resolves exactly the lockfile CI scanned rather than re-resolving to something newer. |
| T-01-46 | Spoofing | a reboot test reported without a reboot | high | mitigate | The evidence is a boot timestamp from `uptime -s` compared against the application's own `boot_time`, not merely a green `systemctl is-active`. Recorded as a prohibition in `must_haves.prohibitions`. |
| T-01-47 | Denial of Service | the reboot itself, on a box serving a live site | medium | mitigate | The pre-resize snapshot and the stopped old instance are confirmed intact before the reboot, so a box that does not come back has a recovery path; the post-reboot checks include Apache, the database and vockell.com, not only the new service. |
