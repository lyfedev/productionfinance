<objective>
Resize the shared Lightsail box from its current bundle to 2 GB by snapshot-and-restore, preserving the static IP, with the live vockell.com site down for a measured, deliberately scheduled window and a working rollback the whole time.

Purpose: PROJECT.md measured this box on 2026-08-24 at 472 MB of memory with 95 MB already in swap at idle. That cannot hold FastAPI plus a Python runtime alongside the existing Apache and MySQL, so the resize is not optional. Lightsail cannot resize in place — a snapshot restored onto a larger bundle is the mechanism, and the static IP can only be attached to one instance at a time, so the swap takes the live site offline. STATE.md flags this as a discrete, schedulable task rather than something to stumble into, and MEMORY records that provisioning a billable resource needs explicit per-resource approval.

Output: A 2 GB, 2 vCPU instance serving vockell.com on the same static IP, the old instance stopped and retained as rollback, and the measured downtime recorded.
</objective>

<task type="checkpoint:decision" gate="blocking-human">
  <decision>Authorise provisioning a 2 GB Lightsail instance and schedule the vockell.com downtime window</decision>
  <context>
    Two separate approvals are bundled here because they are the same action. Task 1 has already recorded the exact current bundle and the `small_3_0` bundle with their monthly prices — read those figures out of the "Preflight inventory" section of `deploy/README.md` before answering; this checkpoint is not asking you to approve an abstraction.

    **The spend.** Creating an instance from a snapshot at `small_3_0` provisions a new, larger, more expensive Lightsail instance. The old instance keeps billing while it is retained as rollback, so for the remainder of this phase you are paying for both, plus a snapshot. Your standing rule is that no cloud resource is provisioned without explicit per-resource approval and that an instruction to proceed with work is never authorisation to spend money — so this is the approval, with the actual figures in front of you.

    **The downtime.** Lightsail cannot resize in place. The mechanism is: snapshot the current instance, create a new instance from that snapshot at the larger bundle, then move the static IP. A static IP can only be attached to one instance at a time, so from the moment it detaches until it is attached to the booted new instance and Apache is serving, **vockell.com is down**. That is your live personal site. The window is typically a few minutes but depends on how fast the restored instance boots.

    **Why it is not optional.** PROJECT.md measured this box at 472 MB with 95 MB already in swap at idle, 1 vCPU, Python 3.9.2. `google-adk` and `google-genai` both require Python 3.10 or newer, and 472 MB cannot hold FastAPI plus a modern Python alongside the existing Apache and MySQL. Without the resize there is no hosted URL, and a hosted URL is the submission's Definition of Done.

    **The rollback.** The snapshot is taken first and is the recovery path. The old instance is stopped rather than deleted, so if the restored instance does not boot cleanly, re-attaching the static IP to the old instance restores the site. Nothing is deleted during this phase.

    **What is not affected.** IPv4 static-IP binding is preserved by this mechanism, so no DNS change is needed and the record created in plan 01-06 keeps working. Plans 01-01 through 01-05 are independent and continue regardless of what you decide here.

  <action>
Run the swap, in this order, checking each step before starting the next. Every command targets the resource names recorded in the preflight inventory, never the names documented in CLAUDE.md.

Take the snapshot first, because it is the rollback path and there is no point starting without one. Name it with a `pre-resize` prefix and today's date so it is unmistakable in the console. Poll `get-instance-snapshot` until its state reports `available`. Do not proceed on a snapshot still reporting `pending` — a restore from an incomplete snapshot is the failure mode with no recovery.

Create the new instance from that snapshot with `create-instances-from-snapshot`, using bundle id `small_3_0`, the same availability zone the preflight recorded, and a name that makes its size obvious. Poll `get-instance` until its state reports `running`.

Before moving the static IP, confirm the new instance is genuinely healthy on its own temporary public address: SSH in and check that Apache and MySQL are running and that `free -h` reports roughly 2 GB. A restored instance that boots but whose services did not come up is exactly the case where moving the IP turns a private problem into a public outage.

Start the downtime clock, then detach the static IP from the old instance and attach it to the new one, using the static IP *resource name* from the preflight inventory. Immediately poll `curl -I https://vockell.com` until it returns 200, and stop the clock at the first success. Record the elapsed window.

Verify the swap landed cleanly: `curl -I https://vockell.com` returns 200; `dig +short A vockell.com` and `dig +short A $PRODFIN_HOST` both still return `35.165.60.123`; SSH to `$PRODFIN_STATIC_IP` reaches the new instance and `free -h` reports roughly 2 GB with 2 vCPU visible in `nproc`.

Record in `deploy/README.md` under a "Rollback" heading the exact sequence to reverse the swap: re-attach the static IP resource to the old instance name, start it, confirm vockell.com serves.

If the restored instance fails to boot cleanly or fails the health check before the IP moves, do not move the IP. Report the failure, leave the old instance running and serving, and treat the new instance as disposable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AWS control plane → live production host | A single API call here takes a third party's live site offline or replaces it |
| snapshot artefact → new instance | The snapshot carries the live site's filesystem, database and any credentials on it |
| public internet → the new instance's temporary address | Between restore and IP swap, the restored instance is reachable on its own public address |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-34 | Denial of Service | vockell.com during the static-IP swap | high | mitigate | The snapshot is taken and confirmed `available` before anything else; the restored instance is health-checked on its own address before the IP moves; the old instance is stopped rather than deleted so re-attaching the IP is a working rollback; the window is measured rather than assumed. The checkpoint makes the outage a scheduled decision rather than a surprise. |
| T-01-35 | Denial of Service | restoring from an incomplete snapshot | high | mitigate | Poll `get-instance-snapshot` for state `available` and refuse to proceed on `pending`. Named explicitly in the action rather than left to the executor's judgment. |
| T-01-36 | Information Disclosure | the instance snapshot | medium | mitigate | The snapshot contains the live site's filesystem and database. It stays private within the AWS account and is never shared to another account or made public. No snapshot-sharing command appears anywhere in this plan. |
| T-01-37 | Information Disclosure | the restored instance exposed on a temporary public address before the swap | medium | accept | It is a byte-identical copy of a box already publicly serving the same content on the same software, reachable for minutes on an address nobody has been told. Accepted at ASVS L1; the mitigation would be a firewall rule whose own risk of misconfiguration exceeds the exposure. |
| T-01-38 | Spoofing | issuing a TLS certificate against a box about to be replaced | medium | mitigate | D-21 sequences the resize before any certificate work, and plan 01-09 runs after this one; no issuance command appears in this plan. |
| T-01-39 | Elevation of Privilege | AWS credentials with Lightsail write access | medium | transfer | The `newaccount` profile's scope and the account's own access controls are the developer's; this plan uses the profile as given and confines itself to the six named Lightsail operations. |
| T-01-40 | Repudiation | provisioning a billable resource without approval | high | mitigate | The preflight surfaces the actual monthly price of both bundles, and the `blocking-human` decision checkpoint requires explicit authorisation with those figures visible. | T-01-SC | Tampering | package-manager installs | high | mitigate | No package installs in this plan. The Phase 1 dependency audit lives in 01-RESEARCH.md § "Package Legitimacy Audit" — all Approved, no `[SLOP]`, no genuine risk signal. |
