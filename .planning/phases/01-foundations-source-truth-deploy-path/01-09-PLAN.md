<objective>
Put Apache in front of the application on the confirmed subdomain, terminate TLS with the tool Bitnami's own layout expects, and prove an anonymous visitor from outside the box gets a 200 over a valid chain — without disturbing the live site sharing the same Apache.

Purpose: this is the last link in ROADMAP Phase 1 success criterion 3 and the point at which the phase's deploy half becomes a hosted URL a judge can visit. It is also the highest-blast-radius step in the phase: `bncert-tool` rewrites Apache's TLS configuration, and vockell.com's live certificate is in the same configuration. D-16 chose certbot-with-Apache over Caddy because Apache holds ports 80 and 443 and Caddy's whole advantage is automatic TLS when it owns 443; the research kept that reasoning and corrected the tool, because a bare certbot Apache-plugin invocation is a documented source of broken configs on Bitnami stacks whose Apache does not live where the plugin looks.

Output: A committed reverse-proxy vhost, a Let's Encrypt certificate covering the subdomain, automatic renewal verified as an actual job on the host, and an external HTTPS probe returning 200 with no certificate warning.
</objective>

  <context>
    This is the one step in the phase that modifies configuration the live vockell.com site is already depending on, so it is being asked rather than assumed. Read the facts Task 1 and the 01-07 preflight recorded into `deploy/README.md` before answering — in particular the existing certificate's domain list, which determines whether option A is safe.

    **What is settled.** D-16 rules out Caddy, and that reasoning stands: Caddy's whole advantage is automatic TLS when it owns ports 80 and 443, and Apache holds those ports for the live site, so running Caddy on an inner port would mean two web servers on a 2 GB box for no gain.

    **What the research corrected.** D-16 named "certbot with the Apache plugin". 01-RESEARCH.md found that a bare `certbot --apache` invocation is a documented source of failed or broken configurations on Bitnami stacks, because Bitnami's Apache lives at a non-standard filesystem path that the standard plugin's auto-detection is not built to find. Bitnami ships its own tool for exactly this, `bncert-tool`, which knows the layout and installs its own renewal job. So "certbot" in D-16 is best read as shorthand for the Apache-integrated Let's Encrypt path rather than a literal package.

    **What is not settled, and is why you are being asked.** 01-RESEARCH.md left one item open: whether re-running `bncert-tool` to add the new subdomain requires re-specifying vockell.com's existing domains in the same invocation, or can be run additively. If it is not additive and the existing domains are omitted, the live site's certificate coverage could be replaced rather than extended. A fresh snapshot was taken in Task 1 precisely because of this uncertainty.

    Whichever option you choose, verification afterwards asserts that `https://vockell.com` still serves over a valid chain — a broken live site is not an acceptable outcome of adding a subdomain, and the rollback is the `pre-tls` snapshot.
  </context>
